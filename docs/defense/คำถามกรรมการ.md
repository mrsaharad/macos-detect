## 2. คำถามที่น่าจะโดน

### ปัญหาและขอบเขต

| คำถาม | แนวตอบ | หัวข้อ |
|---|---|---|
| macOS มี Gatekeeper กับ XProtect แล้ว ทำไมต้องทำระบบนี้ | สองระบบนั้นตัดสินที่ตัวไฟล์ (ลายเซ็น, YARA) แต่การโจมตีแบบ Living off the Land ใช้โปรแกรมของ Apple ที่มีลายเซ็นถูกต้อง จึงต้องดูพฤติกรรมแทน | 1.1, 2.2.1 |
| ทำไมใช้ eslogger ไม่เขียน ES client เอง | ES client ต้องขอ entitlement จาก Apple ซึ่งเกินขอบเขต ส่วน eslogger มากับระบบ ใครก็ทำซ้ำงานนี้ได้ | 2.2.3, 2.5.3 |
| Apple บอกว่า eslogger ไม่ได้มีไว้ให้แอปใช้ จะเชื่อถือได้ไหม | ยอมรับว่ารูปแบบผลลัพธ์อาจเปลี่ยน จึงแยกส่วน Normalizer ไว้ที่เดียว ถ้า Apple เปลี่ยนก็แก้แค่ไฟล์เดียว และตรวจโครงสร้างกับข้อมูลจริงบน macOS 27.2 แล้ว | 2.2.3, 5.2 |
| ทำไมไม่บล็อกการโจมตี | ต้องใช้เหตุการณ์แบบ AUTH ซึ่งต้องมี entitlement ระบบนี้กำหนดขอบเขตเป็นตรวจจับและแจ้งเตือน และเสนอไว้เป็นงานอนาคต | 1.3, 5.3 |
| ทำไมไม่ใช้ Machine Learning | ข้อมูลโจมตีจริงบน macOS มีน้อย และกรรมการ/ผู้ใช้ต้องตรวจได้ว่ากฎจับเพราะอะไร กฎแบบ Sigma เปิดเผยและอธิบายได้ (ตอบสั้นๆ อย่าเถียงยาว) | 2.1.3, 2.3.1 |

### การวัดผล

| คำถาม | แนวตอบ | หัวข้อ |
|---|---|---|
| แยกชุด dev/eval ยังไง ทำไมต้องแยก | ปรับกฎด้วย dev เท่านั้น ล็อกกฎ (git commit) ก่อนรัน eval ถ้าใช้ชุดเดียวกันจะได้ผลดีเกินจริง dev ได้ 25/33 test แต่ eval ได้ 8/21 คือหลักฐาน | 3.2.2, 4.3 |
| ทำไม Precision 88.9% ถึงไม่ใช่ตัวเลขหลัก | base-rate fallacy: เหตุการณ์ปกติมีมากกว่าการโจมตีหลายแสนเท่า ตัวเลขที่ผู้ดูแลระบบรู้สึกได้คือ FP ต่อชั่วโมง จึงรายงาน 1.5–2.0 รายการ/ชม. เป็นหลัก | 2.3.4, 4.4 |
| 13 หรือ 20 เทคนิคน้อยไป สรุปได้หรือ | จึงรายงานช่วงความเชื่อมั่น 95% (Wilson) ทุกตัว เช่น 38.5% มีช่วง 17.7–64.5% ยอมรับว่ากว้าง เป็นข้อจำกัดของจำนวน test ที่รันอัตโนมัติได้บน macOS | 4.3 |
| Atomic Red Team สะท้อนการโจมตีจริงไหม | ไม่ทั้งหมด เกือบทุก test รันคำสั่งผ่าน shell ซึ่ง exec มองเห็นอยู่แล้ว จึงเขียนข้อจำกัดไว้ใน 4.7 และเพิ่ม evasion test แบบเรียก API เพื่อวัดส่วนที่ไม่รันคำสั่ง | 4.7, 4.11.3 |
| ground truth มาจากไหน | v1: ช่วงเวลาทีละเทคนิค + ตรวจ log ด้วยตา; v2: run_atomic.sh บันทึกเวลาและ exit code ทีละ test แล้วตรวจ log แยก test ที่ไม่ได้ทำงานจริงออก (เช่น 8 test ไม่เกิดผล, 2 test macOS ฆ่าก่อน) | 3.2.2, 4.9 |
| ทดลองบนเครื่องที่ใช้งานจริง ไม่ใช่ VM ปลอดภัยไหม/ข้อมูลปนไหม | เลือกเฉพาะ test ที่ไม่ลบระบบ ไม่ใช้เครือข่าย ไม่ถามรหัสผ่าน (ตารางระดับความเสี่ยง 3.3) และตรวจคืนค่าทุกกลุ่ม ข้อเสียคือมีงานพัฒนาปนในช่วงที่ไม่ได้ทดสอบ จึงแยก baseline ออกมาวัดต่างหาก | 3.2.3, 4.4 |

### ผลลัพธ์ (คำถามหนัก)

| คำถาม | แนวตอบ | หัวข้อ |
|---|---|---|
| **v2 ได้ 0/20 ในชุด hold-out แปลว่าระบบล้มเหลวหรือ** | ไม่ใช่ความล้มเหลวของการมองเห็น ระบบบันทึกเหตุการณ์ครบทุก test (exec 44–136 รายการ/test) แต่ไม่มีกฎรองรับ 18 จาก 20 เทคนิค ผลนี้เป็นข้อค้นพบหลัก: กฎที่เขียนจากชุดทดสอบเล็กครอบคลุมเฉพาะที่เคยเห็น และ 38.5% ของ eval แรกสูงเกินจริงเพราะเทคนิคใกล้ dev ผมตั้งใจออกแบบ hold-out เพื่อหาสิ่งนี้ และไม่ได้แก้กฎหลังเห็นผล | 4.9, 5.1 |
| ทำไมไม่แก้กฎให้ได้คะแนนดีขึ้น | ถ้าแก้หลังเห็น eval2 ตัวเลขจะไม่ใช่การวัดจริงอีกต่อไป (overfitting) งานต่อไปคือเพิ่มกฎแล้ววัดด้วยชุดใหม่ eval3 | 4.9, 5.3 |
| SigmaHQ ได้ 6/20 แต่ของคุณได้ 0 ทำไมไม่ใช้ SigmaHQ ไปเลย | SigmaHQ ครอบคลุมคำสั่ง discovery กว้างกว่า แต่หลบง่าย (evasion eval 1/12) และช่วงพัฒนาแจ้งเตือน 17.10/ชม. เทียบกับ 1.45 ของเรา ผลจึงชี้ว่าต้องใช้ร่วมกัน ไม่ใช่แทนกัน | 4.12 |
| ค่า 9/12 ของ evasion ทำไมรายงานแค่ 6/12 | 3 รูปแบบที่เพิ่มมาจาก MD-0033 อย่างเดียว และกฎนี้ออกแบบจาก variant ชุด dev ที่วางไฟล์ในโฟลเดอร์เดียวกัน จึงไม่อิสระ รายงานทั้งสองค่าแต่ใช้ 6/12 อ้างอิง | 4.11.3 |
| Visibility Gap สรุปว่าอะไร | ใต้ชุดทดสอบนี้ ช่องว่างอยู่ที่กฎ ไม่ใช่ข้อมูล test เดียวที่มองไม่เห็นใน v1 เกิดจากการเลือกไม่เก็บเหตุการณ์เขียนไฟล์ (แก้แล้วใน v2 ด้วย close/truncate) แต่สรุปไปถึงการโจมตีทางเครือข่ายไม่ได้ เพราะ ES ไม่มีเหตุการณ์ TCP/UDP | 4.7 |

| FP จาก Word 76 ครั้ง ทำไมไม่นับใน FP | เกิดนอกช่วง baseline ซึ่งเป็นช่วงที่ใช้วัด แต่รายงานไว้ใน 4.2 เพราะชี้ว่ากฎเชิงผลลัพธ์ต้องมีรายการยกเว้นตามโปรแกรมที่เชื่อถือได้ | 4.2 |

| คำถาม | แนวตอบ | หัวข้อ |
