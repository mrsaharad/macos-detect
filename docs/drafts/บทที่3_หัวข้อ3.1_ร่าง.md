## (ย่อหน้ากล่าวนำบทที่ 3 — วางต่อจากหัว "การออกแบบระบบ" ก่อนหัวข้อ 3.1)

บทนี้นำเสนอการออกแบบระบบตรวจจับภัยคุกคามบน macOS ด้วยข้อมูลระดับระบบปฏิบัติการ โดยเริ่มจากการวิเคราะห์ความต้องการและโครงสร้างการทำงานของระบบในหัวข้อ 3.1 จากนั้นอธิบายลำดับการทำงานของระบบและขั้นตอนการทดสอบในรูปแบบ Flow Chart ในหัวข้อ 3.2 การไหลของข้อมูลระหว่างส่วนต่าง ๆ ผ่าน Context Diagram และ Data Flow Diagram ในหัวข้อ 3.3 การออกแบบฐานข้อมูลและรูปแบบไฟล์กฎตรวจจับในหัวข้อ 3.4 และการออกแบบหน้าจอ Dashboard ในหัวข้อ 3.5

## 3.1 การวิเคราะห์ระบบและโครงสร้างการทำงานของระบบ

จากปัญหาที่กล่าวไว้ในบทที่ 1 ระบบป้องกันที่มาพร้อม macOS อย่าง Gatekeeper และ XProtect ตัดสินจากคุณสมบัติของตัวไฟล์เป็นหลัก จึงไม่ได้ออกแบบมาเพื่อตรวจจับการโจมตีแบบ Living off the Land ที่อาศัยโปรแกรมของระบบซึ่งมีลายเซ็นของ Apple อยู่แล้ว ระบบที่พัฒนาในโครงงานนี้จึงต้องติดตามว่าโปรแกรมต่าง ๆ กำลังทำอะไรในระบบอย่างต่อเนื่อง แล้วนำพฤติกรรมที่พบไปเปรียบเทียบกับกฎตรวจจับที่เปิดเผยและตรวจสอบได้ หากเปรียบเทียบให้เห็นภาพ โปรแกรมป้องกันไวรัสทั่วไปทำหน้าที่คล้ายการตรวจบัตรประจำตัวที่ประตู ส่วนระบบในโครงงานนี้ทำหน้าที่คล้ายกล้องวงจรปิดภายในเครื่อง ที่คอยดูการกระทำของโปรแกรมและแจ้งเตือนเมื่อพบพฤติกรรมที่น่าสงสัย

การวิเคราะห์ระบบเริ่มจากการกำหนดความต้องการของระบบให้สอดคล้องกับวัตถุประสงค์ในหัวข้อ 1.2 แล้วจึงแบ่งระบบออกเป็นส่วนย่อยตามหน้าที่ ความต้องการของระบบแบ่งเป็นความต้องการด้านการทำงาน (Functional Requirements) ซึ่งระบุสิ่งที่ระบบต้องทำได้ และความต้องการด้านอื่นที่ไม่ใช่การทำงาน (Non-functional Requirements) ซึ่งระบุคุณสมบัติและข้อจำกัดที่ระบบต้องเป็นไปตาม ดังแสดงในตารางที่ 3.1

**ตารางที่ 3.1 ความต้องการของระบบ**

| รหัส | ความต้องการ | ส่วนของระบบที่รับผิดชอบ |
|---|---|---|
| **ความต้องการด้านการทำงาน** | | |

ในการวิเคราะห์ยังต้องคำนึงถึงข้อจำกัดของแหล่งข้อมูลที่เลือกใช้ ประการแรก eslogger ต้องรันด้วยสิทธิ์ผู้ดูแลระบบ และโปรแกรมที่เรียกใช้ เช่น Terminal ต้องได้รับสิทธิ์ Full Disk Access ระบบจึงออกแบบให้เริ่มทำงานผ่าน Terminal ด้วยคำสั่ง sudo ประการที่สอง eslogger รับเหตุการณ์ประเภทแจ้งเตือน (NOTIFY) ซึ่งรายงานหลังจากเหตุการณ์เกิดขึ้นแล้ว จึงไม่สามารถใช้อนุมัติหรือปฏิเสธการกระทำล่วงหน้าได้ ข้อจำกัดนี้สอดคล้องกับขอบเขตของโครงงานที่มุ่งเน้นการตรวจจับและแจ้งเตือนเท่านั้น ประการที่สาม Apple ระบุว่ารูปแบบผลลัพธ์ของ eslogger อาจเปลี่ยนแปลงระหว่างเวอร์ชันของระบบปฏิบัติการ ระบบจึงแยกส่วนแปลงข้อมูล (Normalizer) ออกจากส่วนตรวจจับ เพื่อให้การเปลี่ยนแปลงดังกล่าวกระทบเพียงส่วนเดียว

จากความต้องการและข้อจำกัดข้างต้น ระบบแบ่งออกเป็นสองส่วนใหญ่ ส่วนแรกคือระบบตรวจจับ ซึ่งประกอบด้วยส่วนย่อย 5 ส่วนทำงานต่อกันเป็นลำดับในลักษณะท่อส่งข้อมูล (pipeline) ได้แก่ Collector, Normalizer, Rule Engine, Alert Store และ Dashboard โดยพัฒนาด้วยภาษา Python ทั้งหมด ส่วนที่สองคือส่วนจำลองการโจมตี ซึ่งใช้ชุดทดสอบ Atomic Red Team สร้างพฤติกรรมการโจมตีที่ทราบผลล่วงหน้า เพื่อใช้ทดสอบและวัดผลระบบตรวจจับ ทั้งสองส่วนทำงานบนเครื่องเดียวกัน โครงสร้างการทำงานของระบบแสดงดังรูปที่ 3.1 และสรุปหน้าที่ของแต่ละส่วนได้ดังตารางที่ 3.2

### 3.1.1 ส่วนเก็บข้อมูล (Collector)

Collector ทำหน้าที่รับข้อมูลเหตุการณ์จาก Endpoint Security Framework เข้าสู่ระบบ โดยเรียกใช้ eslogger พร้อมระบุประเภทเหตุการณ์ 5 ประเภทที่โครงงานนี้ใช้ ได้แก่ exec, fork, create, rename และ unlink แล้วส่งผลลัพธ์ผ่านท่อ (pipe) ของระบบปฏิบัติการเข้าสู่โปรแกรม Python ที่อ่านข้อมูลจาก standard input ทีละบรรทัด การรับข้อมูลผ่านท่อแทนการเขียนลงไฟล์ก่อนแล้วจึงอ่าน ทำให้ระบบประมวลผลเหตุการณ์ได้ทันทีที่เหตุการณ์เกิดขึ้น ซึ่งจำเป็นต่อการตรวจจับแบบเรียลไทม์และการวัดระยะเวลาในการตรวจจับ เนื่องจาก eslogger ส่งข้อมูลออกในรูปแบบ JSON หนึ่งเหตุการณ์ต่อหนึ่งบรรทัด Collector จึงตรวจสอบว่าแต่ละบรรทัดเป็นข้อมูล JSON ก่อนแปลงเป็นโครงสร้างข้อมูลของ Python และข้ามบรรทัดที่ไม่ใช่ข้อมูลเหตุการณ์ นอกจากนี้ Collector ยังออกแบบให้อ่านข้อมูลจากไฟล์ log ที่บันทึกไว้ล่วงหน้าได้ด้วยวิธีเดียวกัน เพื่อใช้ทดสอบกฎตรวจจับซ้ำกับข้อมูลชุดเดิมโดยไม่ต้องสร้างเหตุการณ์ใหม่ทุกครั้ง

### 3.1.2 ส่วนแปลงข้อมูล (Normalizer)

ข้อมูลที่ได้จาก eslogger มีโครงสร้างซ้อนกันหลายชั้น และตำแหน่งของข้อมูลสำคัญแตกต่างกันไปตามประเภทเหตุการณ์ เช่น เส้นทางของโปรแกรมที่ถูกรันในเหตุการณ์ exec อยู่ที่ event.exec.target.executable.path Normalizer จึงทำหน้าที่ดึงข้อมูลที่จำเป็นออกมาจัดให้อยู่ในโครงสร้างข้อมูลกลางแบบแบนราบชั้นเดียว โดยตั้งชื่อฟิลด์ตามแนวทางของ Sigma เช่น Image สำหรับเส้นทางของโปรแกรม ParentImage สำหรับเส้นทางของโปรแกรมแม่ CommandLine สำหรับคำสั่งพร้อมอาร์กิวเมนต์ และ TargetFilename สำหรับไฟล์ที่ถูกสร้างหรือแก้ไข ร่วมกับข้อมูลประกอบอื่น เช่น เวลาที่เกิดเหตุการณ์ หมายเลขโปรเซส และหมายเลขโปรเซสแม่ การออกแบบนี้ทำให้กฎตรวจจับอ้างอิงเฉพาะชื่อฟิลด์กลาง หาก eslogger เปลี่ยนรูปแบบผลลัพธ์ในอนาคต จะต้องแก้ไขเฉพาะ Normalizer โดยไม่ต้องแก้ไขกฎทั้งหมด รายละเอียดของฟิลด์ทั้งหมดแสดงในหัวข้อ 3.4

ข้อมูลที่ eslogger ให้มาโดยตรงระบุโปรเซสแม่เป็นเพียงหมายเลขโปรเซส (ppid) ไม่ได้ระบุว่าโปรเซสแม่คือโปรแกรมใด Normalizer จึงเก็บตารางจับคู่ระหว่างหมายเลขโปรเซสกับเส้นทางของโปรแกรมไว้ในหน่วยความจำ และปรับปรุงตารางทุกครั้งที่พบเหตุการณ์ exec หรือ fork เพื่อนำมาเติมค่า ParentImage ซึ่งเป็นข้อมูลสำคัญของการตรวจจับเชิงพฤติกรรม อย่างไรก็ตาม หากโปรเซสแม่เริ่มทำงานก่อนที่ระบบจะเริ่มเก็บข้อมูล ระบบจะไม่มีข้อมูลของโปรเซสแม่นั้นในตาราง และค่า ParentImage จะว่างเปล่า ข้อจำกัดนี้นำไปวิเคราะห์เป็นส่วนหนึ่งของ Visibility Gap ในบทที่ 4 นอกจากนี้ Normalizer จะไม่เก็บฟิลด์ตัวแปรสภาพแวดล้อม (environment variables) ของโปรเซส เนื่องจากอาจมีข้อมูลส่วนบุคคลของผู้ใช้งาน

### 3.1.3 ส่วนตรวจจับ (Rule Engine)

Rule Engine ทำหน้าที่ตัดสินว่าเหตุการณ์ใดเป็นพฤติกรรมที่น่าสงสัย โดยอ่านกฎตรวจจับทั้งหมดจากไฟล์ YAML ในโฟลเดอร์กฎเมื่อระบบเริ่มทำงาน แล้วนำเหตุการณ์แต่ละรายการที่ผ่าน Normalizer มาเปรียบเทียบกับเงื่อนไขในส่วน detection ของทุกกฎ เงื่อนไขของกฎประกอบด้วยกลุ่ม selection ซึ่งระบุลักษณะที่ต้องตรงกัน กลุ่ม filter ซึ่งระบุข้อยกเว้นเพื่อลดการแจ้งเตือนเท็จ และ condition ซึ่งระบุวิธีรวมกลุ่มเงื่อนไขด้วยตัวดำเนินการ and, or และ not การเปรียบเทียบค่าในแต่ละฟิลด์รองรับตัวปรับ (modifier) ตามแนวทางของ Sigma ได้แก่ contains, startswith และ endswith ซึ่งช่วยให้กฎยืดหยุ่นกว่าการเปรียบเทียบค่าแบบตรงตัวทั้งหมด เช่น การตรวจจับโปรแกรม security ด้วยเงื่อนไข endswith จะตรงกับเส้นทางของโปรแกรมได้ถูกต้องแม้รูปแบบเส้นทางจะแตกต่างกันเล็กน้อย

เมื่อเหตุการณ์ตรงกับเงื่อนไขของกฎใด Rule Engine จะสร้างการแจ้งเตือนที่ประกอบด้วยรหัสกฎ ระดับความรุนแรง รหัสยุทธวิธีและเทคนิคตาม MITRE ATT&CK เวลาที่เกิดเหตุการณ์ เวลาที่สร้างการแจ้งเตือน และข้อมูลของเหตุการณ์ที่เป็นหลักฐาน แล้วส่งต่อไปยัง Alert Store นอกจากฟิลด์มาตรฐานของ Sigma แล้ว กฎแต่ละข้อยังมีฟิลด์คำอธิบายภาษาไทยที่เข้าใจง่าย สำหรับใช้แสดงผลบน Dashboard โดยระบบออกแบบให้มีกฎไม่น้อยกว่า 20 กฎ ครอบคลุมอย่างน้อย 5 ยุทธวิธีตามที่กำหนดในวัตถุประสงค์

### 3.1.4 ส่วนจัดเก็บข้อมูล (Alert Store)

Alert Store ใช้ฐานข้อมูล SQLite ซึ่งจัดเก็บข้อมูลทั้งหมดไว้ในไฟล์เดียวบนเครื่อง โดยไม่ต้องติดตั้งเซิร์ฟเวอร์ฐานข้อมูลแยก สอดคล้องกับความต้องการให้ระบบทำงานบนเครื่องเดียว ฐานข้อมูลประกอบด้วยตารางหลักสองตาราง ได้แก่ ตาราง events สำหรับเก็บเหตุการณ์ที่ผ่าน Normalizer แล้ว ซึ่งใช้เป็นข้อมูลบริบทในการตรวจสอบย้อนหลังและใช้นับจำนวนเหตุการณ์ปกติในการคำนวณอัตราการแจ้งเตือนเท็จ และตาราง alerts สำหรับเก็บการแจ้งเตือนที่ Rule Engine สร้างขึ้น โดยบันทึกทั้งเวลาที่เกิดเหตุการณ์และเวลาที่สร้างการแจ้งเตือน เพื่อใช้คำนวณระยะเวลาในการตรวจจับตามสมการที่ (2.4) การแยกการจัดเก็บออกจากการแสดงผลยังทำให้ Dashboard อ่านข้อมูลจากฐานข้อมูลได้โดยไม่รบกวนการทำงานของส่วนตรวจจับ โครงสร้างตารางโดยละเอียดแสดงในหัวข้อ 3.4

### 3.1.5 ส่วนแสดงผล (Dashboard)

Dashboard พัฒนาด้วย Streamlit และทำงานบนเครื่องเดียวกัน โดยผู้ใช้งานเปิดดูผ่านเว็บเบราว์เซอร์ Dashboard อ่านข้อมูลจาก Alert Store แล้วแสดงตัวเลขสรุป เช่น จำนวนเหตุการณ์และจำนวนการแจ้งเตือน รายการการแจ้งเตือนพร้อมคำอธิบายภาษาไทยและหลักฐาน เช่น คำสั่งที่ถูกรันและโปรแกรมแม่ที่สั่งรัน รวมถึงกราฟสรุปการแจ้งเตือนแยกตามยุทธวิธีของ MITRE ATT&CK จุดประสงค์ของส่วนนี้คือทำให้ผู้ใช้งานเข้าใจสิ่งที่ระบบตรวจพบได้โดยไม่ต้องอ่านข้อมูลดิบในรูปแบบ JSON หรือสืบค้นฐานข้อมูลโดยตรง เนื่องจาก Dashboard ทำงานเป็นโปรแกรมแยกจากส่วนตรวจจับ หาก Dashboard หยุดทำงาน การเก็บข้อมูลและการตรวจจับจะยังคงดำเนินต่อไปได้ การออกแบบหน้าจอแสดงในหัวข้อ 3.5

### 3.1.6 ส่วนจำลองการโจมตี (Atomic Red Team)

ส่วนจำลองการโจมตีไม่ได้เป็นส่วนหนึ่งของระบบตรวจจับ แต่ทำหน้าที่เป็นแหล่งของพฤติกรรมการโจมตีที่ทราบผลล่วงหน้า (ground truth) สำหรับทดสอบระบบ โครงงานนี้ใช้ Atomic Test ชุดที่ Red Canary ระบุว่ารองรับแพลตฟอร์ม macOS ซึ่งแต่ละชุดระบุรหัสเทคนิคตาม MITRE ATT&CK กำกับไว้ เมื่อรัน Atomic Test ระบบตรวจจับจะเห็นพฤติกรรมนั้นเช่นเดียวกับเหตุการณ์อื่นในเครื่อง ผู้จัดทำบันทึกเวลาที่เริ่มทดสอบและรหัสเทคนิคของแต่ละชุด เพื่อนำไปจับคู่กับการแจ้งเตือนในการนับผล True Positive และ False Negative หลังการทดสอบแต่ละชุดจะรันคำสั่งคืนสภาพ (cleanup) ที่มากับชุดทดสอบ เพื่อให้เครื่องกลับสู่สภาพเดิมก่อนการทดสอบชุดถัดไป ส่วนการวัดอัตราการแจ้งเตือนเท็จจะเก็บข้อมูลในช่วงที่ใช้งานเครื่องตามปกติโดยไม่มีการรันชุดทดสอบ ขั้นตอนการทดสอบโดยละเอียดแสดงในหัวข้อ 3.2
