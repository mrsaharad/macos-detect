## 2. วิธีสร้างและแก้ไฟล์ docx

### 2.1 ขั้นตอนที่ใช้ทุกครั้ง
1. ตรวจว่า Word ไม่ได้เปิดไฟล์อยู่ (ไม่มี `docs/~$…docx`) และขนาด/เวลาไฟล์ตรงกับครั้งล่าสุดที่เขียน — ถ้าไม่ตรง แปลว่าผู้ใช้แก้เอง ต้องเริ่มจากไฟล์นั้น
2. สำรองก่อน: `docs/drafts/สำรอง_ก่อน<งาน>_YYYY-MM-DD.docx`
3. `unzip` ไปโฟลเดอร์ทำงาน → แก้ `word/document.xml` (และ `word/_rels/document.xml.rels`, `word/media/` ถ้าเพิ่มรูป)
4. zip กลับด้วย `zip -X -D -r out.docx .` (ไม่ใส่ entry ของโฟลเดอร์)
5. validate (แชท Word ใช้ `validate.py` ของ docx skill — error `w:hint="cs"` 2 จุดมีอยู่แล้วในไฟล์ต้นฉบับ ไม่ต้องสนใจ)
6. render เป็น PDF ด้วย LibreOffice แล้วดูภาพ — **จำนวนหน้าใน LibreOffice มากกว่า Word ~1.5–1.75 เท่า** เพราะไม่มีฟอนต์ TH Sarabun New ให้เชื่อเลขหน้าจาก Word (เคยพลาด: บอก 70 หน้า จริง 40)

### 2.4 กับดักที่เคยเจอ
1. ข้อความหนึ่งประโยคอาจแตกหลาย run (เช่น "ตารางที่ " กับ "3.2" คนละ run) → ค้นหาที่ระดับย่อหน้า ไม่ใช่ใน XML ตรงๆ
2. ข้อความที่ดึงจาก XML มี `&amp;` (ATT&CK) — แปลงก่อนเทียบ และ `escape()` ก่อนเขียนกลับ
3. `rewrite_para` รวมทั้งย่อหน้าเป็น run เดียว → ตัวเอียง/ตัวหนาภายในย่อหน้าหาย ใช้กับย่อหน้าเนื้อหาธรรมดาเท่านั้น
4. ลำดับลูกใน `tblPr`: tblStyle → tblW → jc → tblBorders → **tblLayout** → tblCellMar → tblLook (ผิดลำดับ validate ไม่ผ่าน)
5. ลำดับลูกใน `sectPr` (ข้อ 1.4) — pgNumType ต้องอยู่หลัง pgMar
6. ฟอนต์ไทย: ต้องตั้ง `w:cs="TH Sarabun New"` และ `szCs` ทุก run ไม่งั้นข้อความไทยใช้ Angsana New (Normal style ตั้ง cs เป็น Angsana New)
7. LibreOffice เลขหน้าแบบ thaiLetters ข้าม "ช" — Word ไม่เป็น
8. Word เปิดไฟล์อยู่ = มี `~$` lock → ห้ามเขียนทับ
9. **เลขตารางบทที่ 3**: ตารางระดับความเสี่ยงใน 3.2.3 เคยเป็น "3.10" ทั้งที่อยู่ก่อน 3.3 — แก้แล้ว (เป็น 3.3 และเลื่อนเดิม 3.3–3.9 เป็น 3.4–3.10 รวมข้อความอ้างทั้งหมด) ถ้าเพิ่มตาราง/รูปใหม่กลางบท ต้องเลื่อนเลขและข้อความอ้างทุกจุด
10. บนเครื่อง Mac ผ่าน device bridge ลบไฟล์ไม่ได้ (ต้องขอสิทธิ์) → เขียนทับด้วย `tar xzOf file.tgz path > path`
11. Playwright ใน container โหลดฟอนต์ด้วย `set_content` ไม่ได้ → รูปใช้ฟอนต์ Sarabun woff2 ผ่าน `@font-face file://` (ใน `flow.py`)

### 4.2 สไตล์การเขียนที่ใช้/ผู้ใช้ชอบ
- ประโยควิชาการสั้น ตรง ไม่ขายของ ไม่ใช้คำฟุ่มเฟือย; ตัวเลขทุกตัวต้องมีที่มา
- **ห้ามเขียนข้อมูลที่ยังไม่ยืนยันเหมือนเป็นข้อเท็จจริง** (ผู้ใช้ย้ำ) — ถ้าไม่แน่ใจใส่ร่างสีเทาหรือถาม
- ตอบผู้ใช้: ภาษาไทยเสมอ สั้น ทีละขั้น มีตาราง (ผู้ใช้บอก "ข้อมูลล้นรับไม่ไหว")
- ผู้ใช้กำลังสอบ ต้องการให้ Claude ทำงานให้เร็ว แล้วจะกลับมาเรียน SQL/Python ทีหลัง (`docs/HOW_TO_READ.md`)

### 4.3 สิ่งที่ผู้ใช้สั่ง ห้าม หรือตัดสินใจแล้ว
- ห้ามคัดลอกข้อมูลจาก `data/atomic_logs/` ลงเล่ม (มีข้อมูลเครื่องส่วนตัว); ห้ามแสดง/commit ฟิลด์ `env` ของ eslogger
- กฎ 26 ข้อล็อกตั้งแต่เริ่ม eval (commit 836b891) — ห้ามแก้กฎแล้วใช้ผลเดิม
- ใช้ ATT&CK **v19** ตลอดเล่ม; ATT&CK v20 ออก 13 ต.ค. 2569 — ผู้ใช้สั่งให้เขียนเป็นข้อจำกัดในบท 5.2 (ใส่แล้ว)
- **baseline ใหม่ 8 ชั่วโมง** แทน 60 นาที (ผู้ใช้ตัดสิน 22 พ.ย.; "เรื่องทดสอบเอาไว้ก่อน" 23 พ.ย.) — ยังไม่ได้ทำ; ต้องตัดสินว่ารวม 60 นาทีเดิมหรือไม่
- **เปิด collector ต่อเนื่องให้ครบ 24 ชั่วโมง** เพื่อให้ตรงแผนงานบทที่ 1 (ผู้ใช้เลือก 23 พ.ย.) — ยังไม่ได้ทำ; รวมกับ baseline ได้
- ตาราง 2.3 (Navigator + Detection Rate แยก Tactic): ผู้ใช้จะทำเอง เว้นไว้
- Dashboard ภาษาอังกฤษ ไม่มี emoji ฟอนต์ Sarabun; เสียงด้วย afplay ห้าม osascript (MD-0006 จับวน); Dashboard ห้ามรันคำสั่ง (เคยทำให้ MD-0022 จับตัวเอง)
- ไม่รัน T1555.001 อัตโนมัติ; ไม่เขียนสคริปต์โจมตีเอง ใช้ Atomic ทางการ
- การอ้าง IDC เปลี่ยนจาก Dediu เป็น Mendes (9to5Mac) — ผู้ใช้เลือก 23 พ.ย. (หาแหล่ง Dediu ไม่เจอ)

**ถ้าทำ baseline 8 ชม. ต้องแก้ในเล่ม:** 3.2.2 (ย่อหน้า "หลังตรวจสอบผลของแต่ละชุด…60 นาที"), 3.2.3 ("การแจ้งเตือนเท็จช่วง baseline", "การรันกฎย้อนหลัง" ที่เขียนว่า 60 นาทีสั้นเกิน), รูป 3.3 (กล่อง "ใช้งานเครื่องตามปกติ 60 นาที" — แก้ใน `fig33b.py`), ตาราง 4.1 (ช่วงเวลา), 4.4 ทั้งหัวข้อ + ตาราง 4.5, ตาราง 4.10, 5.1 ข้อ 3, บทคัดย่อ/Abstract ย่อหน้า 3, ภาคผนวก ก (`baseline.sh 60`), Precision (16/18 จะเปลี่ยน), ตาราง 4.6 replay อาจเปลี่ยนเพราะช่วง baseline ถูกตัดออกจาก replay; ถ้าวัด overhead ใหม่ → ตาราง 4.8 และย่อหน้าใน 4.6
