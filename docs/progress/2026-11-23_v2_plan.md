## ทดสอบการป้องกันตัวเอง (23 พ.ย. 2569 18:45 น., daemon v2 ติดตั้งด้วย deploy/install_daemon.sh)
daemon ทำงานด้วย root (Python 3.9 ของระบบ + eslogger เป็นลูก), Full Disk Access ผ่าน, เก็บ event ทุกชนิดรวม close/truncate/setextattr
ลองโจมตีตัวระบบด้วยสิทธิ์ผู้ใช้ทั่วไป (ผู้ใช้เป็น admin แต่ไม่ใช้ sudo) — **ถูกปฏิเสธทั้ง 6 ทาง**:
| วิธี | ผล |
|---|---|
| kill -9 collector | operation not permitted |
| kill -9 eslogger | operation not permitted |
| ลบ alert ในฐานข้อมูล | attempt to write a readonly database |
| แก้ไฟล์กฎ | permission denied |
| ลบไฟล์กฎ | permission denied |
| launchctl bootout daemon | Operation not permitted |
ยังเหลือทดสอบ: KeepAlive (ให้ผู้ใช้ `sudo kill -9` แล้วดูว่า launchd เปิดใหม่และ Dashboard แสดง heartbeat ต่อ)
ข้อจำกัด: ผู้โจมตีที่ได้ root ยังปิดได้ (อยู่นอก threat model)

### สาเหตุ lag ตอนโหลดสูง (24 พ.ย. 2569)
- ตาราง health ช่วง stress: eslogger ส่งมา ~520–640k บรรทัด/นาที (~10.6k/วินาที) คงที่เหมือนชนเพดาน แต่เก็บลงฐานข้อมูลแค่ 5–15k/นาที → ~40 บรรทัดต่อโปรเซส ส่วนใหญ่เป็น `close` ที่ไม่ได้แก้ไฟล์ (ทิ้งทันที)
- วัด CPU ระหว่างสร้าง 6,000 โปรเซส: **eslogger 96–100% (เต็ม 1 คอร์)**, collector Python 42–52% → คอขวดคือ eslogger แปลง event เป็น JSON ไม่ทัน ไม่ใช่โค้ด Python
- ตัวกรองบรรทัดใน Python เร็ว ~100k บรรทัด/วินาที; profile แบบ offline ~4k event ที่เก็บ/วินาที (กฎ 52%, SQLite autocommit 28%) — ยังไม่ใช่คอขวดที่โหลดนี้
- v1 ไม่ subscribe `close` จึงไม่เจอปัญหา; event ไม่หล่นเพราะ ES เก็บคิวไว้ให้ → กลายเป็น lag แทน
- ทางแก้ที่เสนอ: แยก eslogger เป็น 2 โปรเซส (exec/fork/exit/... กับ close) ให้ event สำคัญไม่ต้องรอคิว close; หรือเลิก subscribe close แล้วพึ่ง create/rename/truncate
